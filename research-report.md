### Limitations of the method, verified empirically

1. **Rules are not reconstructed per commit.** The history is measured with a single, present-day specification, because reconstructing the rules would measure changes in the rules rather than changes in the code. Consequence: violations predating the introduction of a rule are anachronistic.
2. **`--today` governs exemption expiry only.** Because all exemptions expire after the end of the measurement window, in this history it is a verified no-op.
3. **`units.registry_policy: exact` aborts every historical tree** with exit code 3 before it runs any rule at all. Without relaxation to `open` the whole study would return zero findings for all 69 commits. The relaxation is byte-level neutral on the frozen workspace.

## 5. Defects revealed by the studies

Running the studies revealed defects both in the harness and in limen itself. They are recorded because they affect the interpretation of the numbers and because they are a result in their own right.

**In the research harness (fixed, with gates added):**

1. The zero-unclassified-differences gate did not exist in the corpus path — `main()` always returned 0. Once added, it fired immediately on 7 real cases.
2. Category C3 cited deviation identifiers that existed only in the translators' code, not in `docs/deviations.md`. A second gate was added that rejects a C3 pointing at a non-existent entry.
3. The per-kind aggregation copied the whole repository table into every rule kind from that repository's specification, counting the same findings repeatedly and mixing kinds. Replaced by per-finding attribution.
4. The import-linter translator built globs without the root prefix, so layer rules could not match any file.

**In limen:**

5. The regex `^\s*` in the Python extractor allowed `\s` to match a newline, understating import line numbers by the number of blank lines above. Fixed; Study 1 unchanged bit for bit.
6. The fact cache keyed by file content did not invalidate after a change to the extractor code.
7. `sys.executable` passed as a relative path could start a different interpreter in a subprocess.

### Main result: the primary measure is degenerate

| Quantity | Value |
| --- | ---: |
| runs in total | 25 |
| runs with a non-zero change in the error count | 2 |
| fraction of runs with zero | 0.92 |
| event rate [95% CI] | 0.08 [0.022, 0.250] |
| runs reducing the error count | 0 |

The `limen check` error count relative to the parent tree **has no between-task variance in any of the six contrasts**, so the paired permutation test degenerates (p = 1). No K and no R will detect a difference in the means of this measure. The cause is measured, not surmised: all parent trees have zero errors on the rules **shown** to the agent — the entire historical debt sits on the held-out rules — and the tasks are small changes inside a single module, whereas the rules enforce boundaries **between** modules. An agent that correctly carries out its assignment has no way of violating them.

This is a defect in the construction of the measure, detected for 21% of the budget of the full study — and the main value of this pilot.

### Co-primary measure and circularity controls

A functional regression occurred in 0.32 of runs [95% CI 0.17, 0.52], but the Wilson intervals overlap in every pair of conditions — this is a measure that **does** have variance and is suitable as the primary measure in a full study.

Finding verification: 50 items from 13 rules, stratified sampling by `rule_id` (seed 20260807). The mechanical rater judged 50/50 to be real; the cited file exists in 50/50 cases, the target occurs in the file in 49, and on the cited line in 46. **A protocol requirement is not met:** two-rater agreement was not computed — the second rater is implemented and seeded, but there was no budget left to run it.

### Power analysis — what a full study would require

The primary measure cannot be strengthened by sample size. Two others are answerable:

| Question | Runs per arm |
| --- | ---: |
| functional regression 0.40 vs 0.15 | 49 |
| functional regression 0.40 vs 0.20 | 82 |
| event rate 0.30 vs 0.10 | 62 |
| event rate 0.20 vs 0.05 | 76 |

That corresponds to K = 20 at R = 3–5 — precisely the variant originally rejected as too costly. A full run only makes sense, however, on condition of **a change in the construction of the tasks**: they must touch more than one module, otherwise the primary measure will stay at the floor regardless of sample size.

### Design defects detected by the pilot

1. **Floor of the primary measure** — described above.
2. **Task `fe-08`**: in every run the agent correctly refused to implement it, because the prompt describes a function of the `reviews` module while the source commit touches `projects`. An error in the construction of the task, not in the agent's behaviour — the selection filter must check that the content of the prompt matches the commit's paths.
3. **Budget**: 25 cells consumed 1,507,477 input tokens (summed over the run records, on average 60,299 per cell); the full 120 cells do not fit in one session. A full study requires splitting into sessions — the plan is frozen (`eval/results/study3_plan.json`) and the runs are incremental, so resuming adds the missing cells without repeating the ones already done.

## 6b. Second pilot — task-selection gate

```bash
python eval/study3_agent/run.py --pool layer1 --condition A --reps 3
```

The first pilot did not settle whether the cause of the zero variance was task selection or the absence of an effect. The second pilot tests **the control condition only**: whether an agent with no rules at all is able to violate the architecture on tasks with a documented violation. If it is not able to, a full study has nothing to measure. Threshold adopted before the start: 0.30.

| Measure | Result | 95% CI (Wilson) |
| --- | ---: | --- |
| **violation of any rule (gate)** | **3/18 = 0.167** | [0.058, 0.392] |
| violation of a held-out rule | 0/18 = 0.000 | [0.000, 0.176] |
| violation of the rule the human violated | 0/18 = 0.000 | [0.000, 0.176] |
| module-boundary crossing (where boundaries exist) | 1/12 = 0.083 | [0.015, 0.354] |
| functional regression | 7/18 = 0.389 | — |

**The gate did NOT pass.** The upper bound of the interval (0.392) does not exclude the threshold of 0.30, so this is a "not shown" result, not a "shown to be absent" one.

### The cause differs from the one in the first pilot

The necessary condition from the study design — the parent tree must have held-out rules that can be violated — was this time **checked and satisfied in all six tasks** (11–14 of the 18 held-out rules violable on each tree). In the first pilot it was not checked and it was breached. The rules could therefore have fired.

What failed was the assumption that a commit in which a **human** crossed a boundary would tempt a **model** to cross it too. The mechanism measurement settles this: in 11 of 12 runs on trees that have module boundaries the agent **added not a single import across a boundary** — it solved the task inside its own module, building a local mechanism instead of reaching for the existing one elsewhere that the human reached for. A rule cannot fire on code that never comes near it.

In 0/18 runs the agent violated the rule violated by the human — **every hypothesis of the author about a tempting boundary was refuted**. The only violations observed were incidental K8 pattern prohibitions in a large new frontend file (debug output, local fallbacks), that is, not architectural crossings.

### The layer-1 pool is smaller than assumed

Of 7 candidates only **4** could be turned into a task:

| Commit | Usable | Reason for rejection |
| --- | :---: | --- |
| `46bbf692` | yes |  |
| `9cf5ac79` | no | root commit — no parent tree exists, so there is no state on which to pose the task |
| `eab22e21` | no | parent tree predates modularisation (no app/Modules); every violated rule is scoped to app/Modu |
| `c1d3e424` | yes |  |
| `82915ff2` | yes |  |
| `c32d1719` | no | root commit — no parent tree exists, so there is no state on which to pose the task |
| `0334bc8f` | yes |  |

Two commits are roots of the history (no parent tree, nothing on which to pose a task), and one has a parent predating modularisation — that is, exactly the failure mode of the first pilot, this time detected before the run rather than after it.

### Conclusion for the full study

**Do not run the full 320-cell run on this project** — it would spend ~19 million tokens measuring a control arm that mostly cannot fail. The only measure with healthy variance remains functional regression (0.389 here, 0.32 in the first pilot). The gate cost 18 cells and saved 320.
