## The primary measure has no variance

`delta_errors` (errors from `limen check` on the agent's tree minus those on the
parent tree) is **0 in 23 of 25** runs.
The proportion of runs introducing a new error:
**0.08** (Wilson 95% CI
[0.022, 0.250]).

The between-task variance of the differences is **zero for each of the six
contrasts**, so the permutation test enters `all-zero` mode and returns p=1.0 —
not as a negative result, but as a degeneracy: **with this measure no K and no R
will detect a difference of means, because there is nothing to differentiate.**
This is the main methodological observation of the pilot.

Why the floor: all 10 parent trees have
**0 errors on the rules shown** to the agent (the entire historical debt lies on
the held-out rules). The tasks are small, well-scoped changes within a single
module, while the rules enforce boundaries **between** modules. An agent that
correctly implements the assignment within a single module simply has no way to
violate those rules.

## Circularity control

**1. Manual verification of a sample of findings.** **50** findings were drawn
(seed 20260807, stratified by `rule_id`, **13 rules**) from the Study 2 findings
with severity error in the present repositories, excluding `spec-dead-entry` and
`unresolved-dependency` (sampling frame: 125 unique findings at code locations).
Mechanical rater: the cited file exists **50/50**, the cited target occurs in the
file **49/50**, the target is on the cited line **46/50**. Among the findings
whose rule cites a line at all and whose exact historical tree could be
reconstructed: **32/32** (95% CI [0.893, 1.000]). The four departures are 3 rules
that do not cite a line by construction (structure, baseline-snapshot) and 1 case
where the historical tree was unavailable and the frozen workspace, with
different line numbering, was used instead.
**The protocol requirement of AGREEMENT between two raters is NOT met** — the
second rater (LLM) is implemented in `eval/study3_agent/verify_findings.py` and
seeded, but was not run, because the session token limit was already exhausted.
Agreement and Cohen's kappa remain uncomputed.

**2. Independent functional measure** — above; it does not derive from limen.

**3. Held-out rules.** 7 of 36 rules were removed from the specification from
which the contract for conditions C and D is generated, and from the findings
returned to the agent in loop D; scoring is always on the full specification. The
rules were chosen stratified by kind so that both halves contain rules that
actually fire in this code: `host-cross-module-public-surface`, `host-into-core-baseline`, `runtime-console-log`, `modules-have-no-local-deployment`, `support-and-models-module-import-allowlist`, `shared-not-into-host-modules`, `oversized-page-file`.
**Result: 0 new errors on the held-out rules in every condition** (and 0 on the
shown rules apart from 2 runs). At 25 runs this split settles nothing — it
measures the same floor.

## Power analysis — what a full study requires

For the primary measure the question of power is ill-posed (no variance).
Answerable versions:

**The event "a run introduced any new error"** at the observed
proportion of 0.08:
553 runs per condition to detect
a halving; 76 to detect 0.20 vs 0.05.

**Functional regression** at the observed pooled proportion of 0.32:
49 runs per condition for 0.40 vs 0.15 (e.g. K=20, R=3),
82 for 0.40 vs 0.20 (e.g. K=20, R=5),
76 for 0.20 vs 0.05 (e.g. K=20, R=4).
Power 0.80, alpha 0.05 two-sided, normal approximation for two proportions.

All three estimates fall in the range **K=20, R=3-5**, that is, exactly the
originally rejected variant K=20/R=5 (400 runs). At the measured cost of
60299 input tokens per run this is
~24.1M input tokens — feasible only spread over many
sessions or with a raised budget.

## Design recommendations before the full study

1. **The primary measure must have variance.** The present tasks (a small change
   within one module) cannot violate rules that enforce boundaries between
   modules. What is needed is either tasks whose scope inherently crosses a
   module boundary (and then the prompt must describe this without revealing the
   architecture — filter C3 makes that harder), or a measure more sensitive than
   the error count (e.g. distance from the boundary: did the import land in
   Contracts or in a concrete Application class).
2. **Report the floor as a result.** "The agent does not break these rules
   because the tasks give it no opportunity" is information about the contract's
   scope of applicability, not a failure of measurement.
3. **Task fe-08 to be replaced.** In 5 of 5 runs the agent refused to implement
   it, correctly noting that the literature review module is absent from the
   shown set of files (the prompt comes from a commit that touches `projects`,
   but describes a feature from `reviews`). This is a defect of task selection,
   not of agent behaviour — filter C1 looks at the modules touched by the commit,
   not at the modules the content of the assignment requires.
4. **Plan the budget per session.** 60299 input tokens per run x the number of
   cells; 2.0M per session is ~33 cells.

## Limitations

- **L1 Incomplete run** (25/120), unbalanced coverage, no task has the full set
  of conditions. These numbers must not be used to infer differences between
  conditions.
- **L2 Specification anachronism** (as in Study 2): one, today's specification
  for historical trees; `units.registry_policy` relaxed to `open`, because
  `exact` aborts with code 3 before any rule runs.
- **L3 The functional measure is a REGRESSION criterion, not an acceptance
  criterion.** The module suite from the parent tree knows nothing about the
  commissioned feature, so "the agent did not implement the task" passes as a
  success. The measure detects only "the agent broke what was working".
- **L4 Agreement between two raters not computed** (see control 1).
- **L5 One parent tree per task**, composed of contemporaneous commits in the
  remaining repositories — a reconstruction that need never have existed
  simultaneously (as with the `workspace` axis in Study 2).
- **L6 Prompts rewritten by an LLM.** The lexical filter C3 guarantees the
  absence of architectural terms, but does not guarantee that the rewritten
  assignment is a faithful description of the commit; the original message is
  stored in the `source` field of every task for verification.
